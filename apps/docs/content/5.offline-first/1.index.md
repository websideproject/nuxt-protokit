# Offline-First Architecture

protokit is **offline-first by design**. Every write goes to the browser's IndexedDB; no network is involved. The server, when you have one, is a backup, not a gatekeeper.

![Two ProtoTool instances on one Y.js document: an edit in one appears in the other](/screenshots/tab-sync-1440.png)

## The short answer

> **Yes — tools work fully offline.** Y.js + IndexedDB means all reads and writes are local. With `serverSync` on, the full document is pushed to the server as a backup once it has loaded and 30 seconds after the last change; a push that fails while offline is simply skipped, and the next one — after the next edit, or the next page load — carries everything. The client does not pull from the server, so a second device does not see the first one's data.

## How a write flows

```
User types in a field
        │
        ▼
Y.Doc (in memory)
        │  Y.js CRDT update (binary delta)
        ▼
IndexedDB (browser)    ← immediate, no network needed
        │
        │  (serverSync on: 30 s after the last change)
        ▼
POST /api/yjs/sync     ← full-state backup push, errors ignored
```

Every change produces a small Y.js **update** — a compact binary delta encoding only what changed. It is applied to the in-memory `Y.Doc` at once and written to IndexedDB asynchronously, a few milliseconds later. The network push is fire-and-forget and sends the whole document.

The tool works identically on a fast connection, a slow connection, or no connection at all.

## What works offline

### Calculator and estimator tools

Ideal offline case. A user adjusts sliders and inputs on a flight, the tool recalculates, everything saves to IndexedDB. After landing, the next edit or page load pushes the backup.

### Form-heavy tools

Work identically offline. Field values are Y.Map entries written to IndexedDB immediately. Multi-section forms, segmented controls, date pickers — all local-first.

### CRUD collections

Add, edit, delete — all work offline. Items are written to `Y.Array` in IndexedDB. Two open tabs exchange their edits directly, online or not, and Y.js merges them.

### Structured note-taking and assessments

Questionnaire tools, scoring rubrics, and structured data entry work without any connectivity.

### Multiple tabs

The same document open in several tabs of one browser stays in step through `BroadcastChannel`, and Y.js merges concurrent edits. protokit does not sync between devices or users: each device has its own IndexedDB copy, and the server only receives backups.

## The `isReady` flag

The only user-visible consequence of offline-first architecture is `isReady`. When a component first mounts, `IndexeddbPersistence` asynchronously loads stored state. Until loading completes, field values show their schema `default`.

```
mount → isReady: false → render skeleton
IndexedDB loads (10–50 ms) → isReady: true → render stored values
```

`ProtoTool` handles this internally — it shows a spinner until the document has loaded. When you use `usePrototype` or `useProtoDoc` directly, guard with `v-if="isReady"` to prevent a flash of default values:

```vue
<script setup lang="ts">
const { state, isReady } = usePrototype(schema)
</script>

<template>
  <ClientOnly>
    <MySettingsForm v-if="isReady" :state="state" />
    <USkeleton v-else class="h-48" />
  </ClientOnly>
</template>
```

## Y.js CRDT merge semantics

| Scenario | Outcome |
|----------|---------|
| Two tabs set the same field at the same moment | One value wins on both tabs — Y.js picks it by client id, not by time |
| Two tabs add different items | Both items appear |
| Tab A edits an item while Tab B deletes it | The edited item survives — an update replaces the item (delete + insert), and the insert is kept |
| Two tabs edit the same item at the same moment | Both edited copies appear, for the same reason |

Truly simultaneous edits are rare between tabs, because each change reaches the other tab within milliseconds. No conflict resolution logic required.

## Multi-tab sync (without server)

When the same document is open in two browser tabs:

1. Tab A makes a change → applied to its `Y.Doc` → written to IndexedDB and broadcast via `BroadcastChannel`
2. Tab B receives the broadcast → applies the Y.js update → reactive refs update immediately

Both tabs stay in sync without a server round-trip. This works **offline** — `BroadcastChannel` is purely local.

## Server sync details

::callout{color="amber" icon="i-lucide-triangle-alert"}
`protokit` handles the **client side** of persistence only. Server sync requires a compatible backend that implements the Y.js sync API endpoints. You can use the separate **`yjs-sync`** companion module or build the endpoints yourself. Without a backend, set `serverSync: false` — no HTTP calls will be made and all data persists locally via IndexedDB.
::

When `protokit.serverSync` is enabled and a compatible backend is available, `useProtoDoc` pushes the full document once IndexedDB has loaded, and again 30 seconds after the last local change:

```
POST /api/yjs/sync               Stores binary Y.js updates in D1/SQLite
POST /api/yjs/snapshots/create   Creates a deduplicated JSON snapshot
```

Server sync provides:
- **Backup against browser storage loss** — incognito mode, cache clear, browser reinstall (the data is on the server; protokit itself only reads it back during corruption recovery)
- **Corruption recovery** — server snapshots enable restore (see next page)

It does **not** provide cross-device continuity: the client never pulls from the server in normal use.

Configure in `nuxt.config.ts`:

```typescript
protokit: {
  serverSync: true,                    // enabled (default), baseUrl: '/api/yjs'
  serverSync: false,                   // disabled — no HTTP calls at all
  serverSync: { baseUrl: '/api/yjs' }, // custom server implementation
}
```

## What survives what

| Event | Outcome |
|-------|---------|
| Page refresh | ✅ All data preserved (IndexedDB) |
| Tab close and reopen | ✅ All data preserved (IndexedDB) |
| Browser crash | ✅ Preserved, except a change made in the last moments before the crash; a write cut off mid-way can corrupt the store (see Corruption Recovery) |
| Loss of internet for hours | ✅ Everything is local; the first edit or page load after reconnecting pushes the backup |
| Browser storage cleared by user | ⚠️ Local data lost — a server copy exists if a push ran, but the client starts empty |
| Private/incognito window | ⚠️ IndexedDB cleared on close — a server copy exists if a push ran |
| IndexedDB corruption | ⚠️ Auto-detected — recovery modal guides the user |

## Using without the server module

Set `serverSync: false` in `nuxt.config.ts` to run in local-only mode. No HTTP calls are made — not even silent ones:

```typescript
// nuxt.config.ts
protokit: {
  serverSync: false,
}
```

Or disable sync for a single tool with the `disable-sync` prop:

```vue
<ProtoTool :schema="mySchema" disable-sync />
```

The only consequences of disabling server sync:
- No server backup
- No corruption recovery option (no server snapshots to restore from)
- The corruption modal shows only "Start fresh" if IndexedDB is damaged

::callout{color="amber" icon="i-lucide-triangle-alert"}
If you omit `yjs-sync` but leave `serverSync: true` (the default), sync calls will 404 silently. This is harmless — local data is safe — but produces unnecessary network requests. Prefer `serverSync: false` when you know you have no server.
::
