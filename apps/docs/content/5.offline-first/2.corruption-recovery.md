# Corruption Recovery

IndexedDB corruption is rare but real. Browser crashes mid-write, certain browser extensions, and disk-level errors can leave a `y-indexeddb` store in an inconsistent state. protokit detects this automatically and provides a guided recovery flow.

## The error signature

`y-indexeddb` corruption shows up as an unhandled promise rejection with the message `"Unexpected case"` or `"Unexpected end of array"` (lib0's decoder hitting malformed binary). It surfaces when `IndexeddbPersistence` tries to load stored updates.

`y-indexeddb` never passes this error to `whenSynced`, so it cannot be caught at the call site. While a document is still loading, `useProtoDoc` listens for it:

```typescript
window.addEventListener('unhandledrejection', (event) => {
  if (isReady.value) return  // this document already loaded — not its error
  const msg = event.reason?.message ?? ''
  if (msg.includes('Unexpected case') || msg.includes('Unexpected end of array')) {
    event.preventDefault()
    // … recovery flow below
  }
})
```

This covers unencrypted documents. An [encrypted](/offline-first/encryption) store has no recovery flow.

## Recovery flow

```
IndexedDB corruption detected
        │
        ▼
Destroy the provider and delete the corrupted IndexedDB database
        │
        ▼
serverSync on? → GET {baseUrl}/snapshots/{fullKey}?limit=1
        │
        ├── Snapshot found ─────────────────────────────►
        │                                   ProtoCorruptionModal:
        │                                   "Restore from server backup" (with its age)
        │                                   or "Start fresh"
        │                                                │
        │                                   User clicks "Restore"
        │                                                │
        │                                   POST {baseUrl}/snapshots/restore
        │                                     (Y.js method, JSON as fallback)
        │                                   Open a new IndexedDB store
        │                                   GET {baseUrl}/pull → apply to the doc
        │                                   Push the restored state + new snapshot
        │
        └── No snapshot (or sync off) ────────────────►
                                          ProtoCorruptionModal:
                                          "Start fresh" only
                                                       │
                                          Open a new IndexedDB store holding
                                          whatever the in-memory doc already has
                                          (nothing is pushed to the server)
```

"Start fresh" keeps the part of the document that loaded before the error; it is not necessarily empty.

## `ProtoCorruptionModal`

A non-dismissible modal that appears over the full page when corruption is detected. The user must choose an action before continuing.

![The recovery modal after the stored document was corrupted, with no server backup configured](/screenshots/corruption-recovery-modal-1440.png)

Nothing mounts it for you — register it **once** in `app.vue`. Without it, a corrupted document waits for a choice that is never shown:

```vue
<!-- app/app.vue -->
<template>
  <UApp>
    <NuxtPage />
    <ProtoCorruptionModal />
  </UApp>
</template>
```

The modal displays:
- Which document is affected (tool name or doc key)
- Whether a server snapshot exists and how old it is
- Two options: **Restore from server backup** or **Start fresh**

If no server snapshot exists, only "Start fresh (data will be lost)" is shown.

## `useProtoCorruption`

The corruption system uses a module-level singleton queue to decouple detection (in `useProtoDoc`) from display (in `ProtoCorruptionModal`):

```typescript
interface CorruptionEvent {
  id:                  string        // random id for this event
  fullKey:             string        // Y.js doc key, e.g. 'proto:saaskit-idea-abc123'
  displayName:         string        // name shown in the modal
  latestSnapshotId:    string | null // null if no server snapshot exists
  latestSnapshotAge:   number | null // milliseconds since the snapshot was taken
  latestSnapshotLabel: string | null // human-readable label
  syncEnabled:         boolean       // server sync on for this doc — the modal only promises backups when it is
  reason:              string        // raw error message
}
```

Internal flow:

```typescript
// In useProtoDoc — called on "Unexpected case" detection:
const action = await reportCorruption({
  fullKey,
  displayName: docKey,
  latestSnapshotId,     // from GET <syncBase>/snapshots/:key, only when sync is on
  latestSnapshotAge,
  latestSnapshotLabel,
  syncEnabled,
  reason: msg,
})
// reportCorruption returns a Promise that resolves with 'restore' or 'fresh' when the user chooses

// ProtoCorruptionModal calls internally:
resolveCorruption(eventId, 'restore')  // or 'fresh'
```

You should not need to call these functions directly — `useProtoDoc` and `ProtoCorruptionModal` handle the complete flow.

## Server snapshot storage

The `yjs-sync` module stores two representations for each snapshot:

| Format | Purpose |
|--------|---------|
| Binary Y.js updates | CRDT-correct restore — exact document state reconstruction |
| JSON | Human-readable, shown in `ProtoDebugPanel`, used for deduplication |

Snapshots are deduplicated server-side — if the document content has not changed since the last snapshot, a new snapshot is not created.

Snapshots are created after every server push — once the document has loaded, and 30 seconds after the last change. `useProtoDoc` asks for one with `POST {baseUrl}/snapshots/create`; the server decides whether anything changed.

## `ProtoDebugPanel`

Mount it yourself — it is not gated, so render it only in development:

```vue
<!-- app/app.vue -->
<script setup lang="ts">
const isDev = import.meta.dev
</script>

<template>
  <UApp>
    <NuxtPage />
    <ProtoCorruptionModal />
    <ClientOnly v-if="isDev">
      <ProtoDebugPanel />
    </ClientOnly>
  </UApp>
</template>
```

The panel (opened from a fixed tab on the right edge of the viewport) lets you:
- See every open document: key, ref count, ready / IndexedDB / tab-sync / server flags
- Expand a document's content as JSON and copy it
- Delete **all** protokit IndexedDB databases (`proto:*`, plus the older `projects:*` and `idea:*`), after a browser confirm

To test recovery, use the playground's `/corruption-recovery` page, which corrupts a stored document on purpose.

## When recovery cannot restore data

Recovery from a server backup requires both:
1. A compatible sync backend is available and reachable (the `yjs-sync` companion module, or a custom implementation)
2. At least one server sync has completed for that document

If either is missing — for example, the tool was used entirely offline since it was first opened — the modal shows only "Start fresh". Whatever did not load from the corrupted store is lost.

**Mitigation:** Encourage users to work online at least once after creating significant data. Every page load pushes the document and requests a snapshot, and so does every edit after 30 seconds of quiet.

## False positives

`useProtoDoc` only reacts while the document has not finished loading, and only to the two lib0 messages above. There is no further check: an unrelated rejection with the same message, raised while a document is loading, would also open the modal.
