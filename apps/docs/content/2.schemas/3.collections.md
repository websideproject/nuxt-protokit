# Collections

A **collection** is a schema-driven CRUD list. Each collection maps to a `Y.Array` in the Y.js document, so items persist offline in IndexedDB.

![A collection with three items: search, category badge, edit and delete](/screenshots/competitors-1440.png)

## Defining a collection

Collections live in the top-level `collections` key of a `PrototypeSchema` (or stand alone with `useProtoCollection`):

```typescript
collections: {
  entries: {
    key: 'entries',                     // Y.Array name: '<schema.key>:entries' inside a prototype
    title: 'Entries',                   // header, and "Add Entries" / "Edit Entries" in the modal
    icon: 'i-lucide-list',
    itemLabel: item => item.name || 'Untitled',

    fields: {
      name:     { type: 'text', label: 'Name', default: '' },
      category: {
        type: 'select',
        label: 'Category',
        options: [
          { value: 'a', label: 'Type A' },
          { value: 'b', label: 'Type B' },
        ],
        default: 'a',
      },
      score:    { type: 'range',    label: 'Score', min: 1, max: 10, default: 5 },
      notes:    { type: 'textarea', label: 'Notes', default: '' },
    },
    defaults: { name: '', category: 'a', score: 5, notes: '' },

    editMode:  'modal',        // 'inline' (default) | 'modal'
    modalSize: 'xl',           // 'sm' | 'md' | 'lg' | 'xl' | '2xl' | '3xl' | '4xl' | '5xl'

    searchable:   true,
    searchFields: ['name', 'notes'],   // default: every field key
    listDisplay: { primaryField: 'name', badgeField: 'category' },

    maxItems: 100,
  },
}
```

`defaults` is what a new item starts from, and it is merged under every stored item on read — keep it in step with the fields' `default`s.

## The list

`ProtoCrudList` renders the collection's title and icon, an **Add** button, a search box (when `searchable` and there are items), and one row per item with edit and delete buttons. A row shows:

- `listDisplay.primaryField` — or `itemLabel(item)` when `listDisplay` is not set
- `listDisplay.secondaryField` — muted second line
- `listDisplay.badgeField` — a badge on the right

## Edit modes

### `inline` (default)

**Add** and the edit button open a card with the collection's form above the list.

![The inline add form of a collection, built from its fields](/screenshots/competitors-add-1440.png)

### `modal`

**Add** and edit open a `ProtoCrudModal`. Recommended for collections with many fields or long textareas. While a user fills in a **new** item, the modal saves a draft to `Y.Map 'draft:<collection key>'`; if they close it without saving, the next **Add** offers to resume or discard that draft. Editing an existing item keeps no draft.

```typescript
editMode:  'modal',
modalSize: '3xl',   // 'lg' and wider lay the fields out in two columns
```

## Preset packs

Preset packs let users bootstrap a collection with starter items:

```typescript
presets: [
  {
    id: 'starter-pack',
    label: 'Starter Pack',
    icon: 'i-lucide-package',
    description: '3 commonly used entries to get you started',
    items: [
      { name: 'Example Alpha', category: 'a', score: 7 },
      { name: 'Example Beta',  category: 'b', score: 5 },
      { name: 'Example Gamma', category: 'a', score: 8 },
    ],
  },
]
```

Once the collection has items, the presets show as compact buttons above the list. Clicking one asks for confirmation, then adds its items, skipping any that are already there (matched by `id`, then `text`, then the whole item).

## Onboarding presets

Set `onboardingPresets: true` to show the `presets` as large cards on the **empty** collection instead of the plain empty state, with an "Add items manually" option next to them:

```typescript
presets: [ /* … */ ],
onboardingPresets: true,
```

Once items exist, the collection switches to the normal list with the compact preset buttons.

## Using collection data in `derived`

Collection items are available in `ComputeContext.collections`:

```typescript
derived: {
  totalItems: {
    compute: ({ collections }) => collections.entries?.length ?? 0,
  },
  avgScore: {
    compute: ({ collections }) => {
      const items = collections.entries ?? []
      if (!items.length) return null
      return items.reduce((sum, i) => sum + (i.score ?? 0), 0) / items.length
    },
  },
  topEntries: {
    compute: ({ collections }) =>
      (collections.entries ?? [])
        .filter(i => i.score >= 8)
        .map(i => i.name),
  },
}
```

## Schema migration

**Adding a new field** to a collection requires no migration — stored items are merged with `defaults` on read, so the new field gets its default value.

![Three items stored in the v0 shape, migrated to v2 on reload: done becomes status, assignee becomes assigneeId and assigneeName](/screenshots/schema-migration-1440.png)

**Renaming a field, changing its type, or transforming values** requires bumping `version` and providing a `migrations` map. Each key is the **target version** — so if stored data is at v2 and current is v5, the runner applies `migrations[3]`, `migrations[4]`, `migrations[5]` in order. Steps with no entry are skipped.

```typescript
collections: {
  tasks: {
    key: 'tasks',
    title: 'Tasks',
    itemLabel: item => item.assigneeName || 'Task',
    version: 2,
    migrations: {
      // v0 → v1: renamed done:boolean to status:string (destructure out the old field)
      1: ({ done, ...rest }) => ({
        ...rest,
        status: done ? 'done' : 'open',
      }),
      // v1 → v2: split assignee:string into assigneeId + assigneeName (remove old field)
      2: ({ assignee, ...rest }) => ({
        ...rest,
        assigneeId:   assignee?.toLowerCase().replace(/\s+/g, '-') ?? '',
        assigneeName: assignee ?? '',
      }),
    },
    fields: {
      status:       { type: 'select', label: 'Status',        default: 'open', options: ['open', 'done'] },
      assigneeId:   { type: 'text',   label: 'Assignee ID',   default: '' },
      assigneeName: { type: 'text',   label: 'Assignee Name', default: '' },
    },
    defaults: { status: 'open', assigneeId: '', assigneeName: '' },
  },
}
```

Each step function receives one raw stored item — exactly the fields that were written to Y.js, with no defaults applied. Destructure out the old field name and spread the rest to keep the shape clean. The migrated items replace the stored ones in a single transaction, and the version is stamped in a `Y.Map '<array name>:__meta__'`, so later loads skip the steps.

Both `usePrototype` (and `ProtoTool`) and `useProtoCollection` run collection migrations once IndexedDB has loaded the stored items.

## Validation

Add a `validate` function to block saves when an item is invalid. Return `true` to allow saving, a `string` for one error message above the form, a `Record<string, string>` to mark specific fields with their own messages, or `false` for a generic "Please fix the errors before saving."

```typescript
collections: {
  entries: {
    // …
    validate: (item) => {
      const errors: Record<string, string> = {}
      if (!item.name?.trim()) errors.name = 'Name is required.'
      if (item.score < 1 || item.score > 10) errors.score = 'Score must be between 1 and 10.'
      return Object.keys(errors).length ? errors : true
    },
  },
}
```

Both edit modes run it on save. Saving is blocked until it returns `true`.

## Exposing collection aggregates via `produces`

Compute the aggregate in `derived`, then name it in `produces` with its type:

```typescript
produces: {
  avgScore:   'number',
  totalItems: 'number',
  topEntries: 'string[]',
}
```

Each key must be a key of `derived`. Downstream tools can then consume these values without access to the raw collection. See [Connections](/schemas/connections).

## `CollectionSchema` full type

```typescript
interface CollectionSchema {
  key:                string
  title:              string
  icon?:              string
  itemLabel:          (item: Record<string, any>) => string
  fields:             Record<string, FieldDef>
  defaults:           Record<string, any>
  maxItems?:          number          // add() is ignored once reached
  sortBy?:            string          // initial sort key of useProtoCollection's `sorted`
  sortOrder?:         'asc' | 'desc'
  searchable?:        boolean
  searchFields?:      string[]
  editMode?:          'inline' | 'modal'
  modalSize?:         'sm' | 'md' | 'lg' | 'xl' | '2xl' | '3xl' | '4xl' | '5xl'
  presets?:           PresetPack[]
  onboardingPresets?: boolean
  listDisplay?:       { primaryField: string, secondaryField?: string, badgeField?: string, avatarField?: string }
  tableColumns?:      Array<{ key: string, label: string, sortable?: boolean, format?: 'money' | 'percent' | 'number' | 'date' | ((v: any) => string) }>
  validate?:          (item: Record<string, any>) => true | false | string | Record<string, string>
  version?:           number
  migrations?:        Record<number, (item: Record<string, any>) => Record<string, any>>
  permissions?:       CollectionPermissions   // role guards — see Permissions
  statusField?:       StatusFieldDef
  itemActions?:       CollectionItemAction[]
  itemPanels?:        CollectionItemPanel[]
}

interface PresetPack {
  id:           string
  label:        string
  icon?:        string
  description?: string
  color?:       string
  items:        Record<string, any>[]
}
```

`tableColumns` is read by `ProtoCrudTable` (a dashboard `collection` item with `view: 'table'`), which renders a read-only table; `sortable` is not used yet. `avatarField`, `statusField`, `itemActions` and `itemPanels` are part of the type but no built-in component renders them yet — render item panels yourself with the [`ProtoItemPanel*` components](/components/proto-item-panels).
